# Changelog

Fixes go on `main`. Chapter tags never move once published; a chapter whose code had to change gets a new tag alongside the old one, such as `ch08-r2`.

## Unreleased

- Security: CSRF protection is back on everywhere except when `APP_ENV=local`. Tags `ch09` and `ch10` exempted `login` and `support/*` in every environment so the book's `curl -b cookies.txt` flow works; `main` now exempts only `login` and `support/ask`, and only locally. In any other environment, send the `XSRF-TOKEN` cookie value back as the `X-XSRF-TOKEN` header. Do not deploy the `ch09` or `ch10` tags as they stand.
- Fix a flaky `help:search` test at and after `ch06`: `RefreshDatabase` rolls back the bulk inserts of the `help:embed` tests, which leaves dead entries in the HNSW index, and an approximate index scan over a handful of rows could then miss the right chunk. The two search tests now turn off index scans for their transaction so they compare exactly; no application code changed. Test-only, so the `ch06` tag is unaffected.

## ch22

- `php artisan ai:doctor [--provider=local] [--ctx=]` (no `--size`) now runs the chapter's checks against an Ollama server; `--size` is unchanged. It prints one line per check (`✓`, `⚠`, `✗`), then `N warnings, M failures`, and exits 1 on any failure. The checks, in order (`app/Ai/Doctor`, one class each under `Checks/`): reachable and version (stops here if not); the configured models are present, with their resolved quantization, parameter size and digest from `/api/tags`; the `num_ctx` the server will actually use against `ai.budget.window` (fails below it, warns when it is 2x or more above it because the KV cache is allocated for all of it); GPU/CPU placement from `/api/ps` (`size_vram` against `size`); `OLLAMA_NUM_PARALLEL` against the `ai-interactive` Horizon workers; keep-alive; whether port 11434 answers on a non-loopback address; a `/v1/chat/completions` and a native `/api/chat` round trip, the second required to carry `prompt_eval_count` and `eval_count`; license recorded (fail if blank) and reviewed (warn if not). Which providers: `ai.default` (or `--provider`) names the server and the model that is round-tripped; the models checked are the providers in `ai.ollama.providers` (`AI_OLLAMA_CHECK_PROVIDERS`, default `local,local-embed,vision`) that point at the same server.
- How each check knows what it knows, since Ollama does not report its own environment: `num_ctx` is the loaded model's `context_length` from `/api/ps` after the `/v1` round trip (what `/v1` traffic is served at), else the `num_ctx` line of the Modelfile in `/api/show`'s `parameters` text, else "unknown" (a warning, not a guess). Keep-alive is the loaded model's `expires_at` right after a `/v1` request that carries no `keep_alive`: about 5 minutes means the default. `OLLAMA_NUM_PARALLEL` cannot be read from the server at all, so the app declares it in `.env` (`OLLAMA_NUM_PARALLEL`, the same variable the Compose file uses, `ai.ollama.num_parallel`) and the doctor compares that with the worker count and says so when it is not declared. The port check connects to the machine's own non-loopback IPv4 addresses (`net_get_interfaces()`) when Ollama is on localhost (fail on a public address, warn on a private one), and judges the resolved address when Ollama is on another host. When the native path is on and `AI_NUM_CTX` differs from what `/v1` is served at, it warns, because Ollama reloads a model whenever the context changes between requests (below).
- `OllamaDriver` (`app/Ai/Drivers/OllamaDriver.php`, driver name `ollama`): chat over Ollama's native `/api/chat` with `options.num_ctx`, `keep_alive`, `format` (a JSON schema for structured output), tools, images as base64 `images`, and `SupportsContextWindowOverride`. Usage is exact (`prompt_eval_count`, `eval_count`, and `prompt_eval_cached_count` as the cached tokens); `ChatResponse` gained `firstTokenMs` (load + prompt evaluation + one decoded token, as the server reports them) and `UsageLoggingModel` writes it to `model_calls.ttft_ms` for calls that are not streamed (streams keep the client-measured time to the first delta; the server's figure is the fallback). The OpenAI options map to Ollama's (`max_tokens` to `num_predict`, `stop` to a list); anything Ollama has no field for, and `tool_choice`, is dropped with the usual one-time warning. Streaming reads NDJSON (`NdjsonReader`); a streamed tool call arrives whole in one chunk and Ollama still says `done_reason: stop` for it, so the finish reason becomes `tool_calls` when a call was seen. `raw()` sends OpenAI-style paths (`/models`) to `/v1`, so `ai:providers --check` works with it.
- The drop-down the book describes: `OpenAiCompatibleDriver` stays on `/v1/chat/completions` by default and hands a request to an `OllamaDriver` built from the same provider when the endpoint is Ollama (`OllamaEndpoint::isOllama`: `driver` is `ollama`, or the provider's `ollama` flag, `AI_OLLAMA`, or port 11434) and one of three things is set: `withContextWindow()` was called (so `AI_SUMMARY_CONTEXT_WINDOW` now takes effect against Ollama, which it did not through `/v1`), `AI_NUM_CTX` is set (sent on every request), or `AI_OLLAMA_NATIVE=true` (everything native, with `keep_alive` from `AI_OLLAMA_KEEP_ALIVE`, default `30m`; `-1` is sent as the number). Embeddings stay on `/v1/embeddings` (`OpenAiCompatibleEmbeddings` works for `driver=ollama` too); `/api/embed` is not used.

## ch21

- `php artisan ai:doctor --size [--model=] [--provider=] [--ctx=] [--slots=1] [--cache=f16|q8_0|q4_0] [--reserve-gib=0] [--reachable-gib=] [--parameters-billions= --layers= --kv-heads= --head-dim= --quantization=]`. It does the Topic 7 sum, weights plus KV cache (2 x layers x KV heads x head dim x bytes, per token, times context times slots) plus headroom, and compares it with what the GPU can reach. Output: the three terms and the total (with the cache at q8_0 alongside), the reachable memory and where that number came from, the binding term (weights, cache or headroom), a verdict (exit 0 when it fits, 1 when it does not or when the machine or model cannot be sized), and, when it does not fit, what each lever would do (q8_0 cache, one quantization level lower, half the context, one slot) and whether that alone would be enough. `--model` defaults to the provider's model, `--ctx` to `ai.budget.window` (8192). Only `--size` exists: the book also lists other doctor checks (it says Chapter 22 makes `num_ctx` one), so `ai:doctor` without `--size` just says so.
- Where the numbers come from (`app/Ai/Hardware`): the model's architecture and file size come from the server first (Ollama `/api/show` for layers, KV heads and head dimension, `/api/tags` for the real file size, which is the book's "the GGUF file size is the answer"), then from the catalogue in `ai.hardware.architectures` (Llama 3.1 8B, 70B and 405B, and Llama 3.3 70B, with bytes per parameter by quantization from the book's Chapter 23 table in `ai.hardware.quantizations`), then from the options. A model in none of those is refused with the options to pass. Reachable memory is found by `HardwareProbe` through a `HostInspector` (the real one runs `sysctl`, `nvidia-smi`, `rocm-smi`, reads `/proc/meminfo`; tests use `FakeHost`): macOS uses `iogpu.wired_limit_mb` when set, otherwise `ai.hardware.macos_gpu_share` (0.75) of RAM; NVIDIA uses the VRAM `nvidia-smi` reports, summed over cards; AMD uses the `rocm-smi` carve-out plus GTT; a Linux box with neither uses system RAM. `AI_REACHABLE_MEMORY_GIB` (or `--reachable-gib`) replaces any of it. `AI_MEMORY_BANDWIDTH_GBPS` sets the bandwidth, which is not detectable; a handful of Apple chips are looked up from published figures in `ai.hardware.apple_bandwidth_gbps` (M1 Pro 200 GB/s and six others; I left out chips whose bandwidth depends on the GPU core count).
- `php artisan ai:profile --provider=local [--prompts=storage/samples/profile-set.json] [--interval=1] [--max-tokens=256] [--bandwidth-gbps=]`. It streams each prompt of a fixed set (three: one short, one medium, one of about 400 tokens) through `Ai::chat($provider)->stream()` (so the real driver, retries and `model_calls` logging, feature `profile`) while a second process, the hidden command `ai:profile-sample`, writes one JSON memory reading per interval. A second process is needed because PHP cannot sample while it is blocked waiting for the first token, which is exactly when the model loads. The report is a table per sample (second, resident GiB, GPU GiB, phase `idle`/`load`/`prefill`/`decode`, prefill and decode tok/s, context tokens) and a summary: load-to-first-token (only when the model was not already loaded), median prefill over warm prompts, median decode, decode against the ceiling `bandwidth / weight bytes` with the percentage reached, peak resident, peak GPU, bytes spilled to the CPU. Prefill is not reported for a cold prompt, because its wait includes the load. Prompts are independent (each is a fresh conversation), so Ollama's prompt cache does not inflate prefill and the context-token column resets per prompt; context tokens during decode are the prompt tokens plus generated tokens interpolated from when the deltas arrived.
- What `ai:profile` reads, per platform: GPU memory and bytes spilled from Ollama's `/api/ps` (`size_vram`, and `size - size_vram`) on every platform; "resident" from `vm_stat` wired pages on macOS (machine-wide, includes everything else wired, and the command prints that caveat) and from the summed RSS of processes named `ollama` (`ps -axo rss=,comm=`) elsewhere. `powermetrics` (needs root), `rocm-smi` and `nvidia-smi` sampling are not implemented. It needs an Ollama server at the provider's `base_url`; against anything else the GPU and spill columns are zero.

## ch20

- `php artisan ai:compare --providers=local,mid,frontier [--feature=support.reply,ticket.classify] [--golden=] [--limit=N] [--judge=<provider>] [--replay] [--stream] [--output=]`. It builds a set of requests once, sends the same normalized `ChatRequest` to every named provider through `Ai::chat($name)` (so the drivers, retries and `model_calls` logging are the real ones; calls are logged under the feature `compare.{feature}`, so `ai:stats` for `support.reply` stays clean), scores every answer, and prints one table per feature (cases, errors, quality, mean input and output tokens, p50 latency, p50 time to first token with `--stream`, `$/1K requests`, quality per dollar) plus quality by category. The result is saved as `storage/benchmarks/compare-{date}.json` (a second run on the same day gets a time suffix; the files are git-ignored). Providers that are unknown, not chat models, or not configured are refused before anything runs; a provider that fails three cases in a row is given up on and its remaining cases are recorded as errors.
- Cases (`app/Ai/Compare/Cases`): `support.reply` is built from the ch15 golden set (`storage/golden/retrieval.jsonl`, 120 questions) through the real retriever and `SupportPrompt::assemble()`, so the prompt is the one production sends; the case category is the help-center area of the expected article (`billing`, `account`, ...) or `off-topic`. A question whose expected section the retriever did not return is skipped and listed, because no model could be blamed for missing it. `ticket.classify` is built from `storage/samples/tickets.json` (20 labeled messages) with the same prompt and `TicketData` schema `ClassifyTicket` uses; the category is the label. `--limit` spreads its picks evenly through the file (the golden file is ordered by help area, so the first N would be one area). `--replay` takes requests recorded in `recorded_requests` instead (below).
- Scorers (`app/Ai/Compare/Scorers`): `ExactMatchScorer` (the label, from the JSON `category` or a bare word), `RetrievalRecallScorer` (1 when the answer cites a passage that covers an expected golden section, using `CitationChecker` and `RetrievedChunk::covers()`; for an off-topic question 1 when the answer declines and cites nothing, a regex heuristic), and `JudgeScorer` (a judge provider grades 1 to 5 against a rubric, `JudgePrompt`, normalized to 0..1; `--judge`). A case's quality is the mean of its scorers, so with `--judge` a `support.reply` case is the mean of recall and the judge's grade. Chapter 30 generalizes this.
- Cost (`CostModel`): a provider with a non-zero entry in `ai.rates.{provider}.{model}` (USD per million tokens) is priced from its token counts; otherwise one with `gpu_hour_cost` (`AI_GPU_HOUR_COST`, `MID_GPU_HOUR_COST`) pays that hourly price times the wall-clock time of the request, one request at a time with no batching (an upper bound against a batched server); a local server with neither prints `$0.00*` (a footnote says why); a hosted provider with no rate prints `no rate` and no quality per dollar, instead of a false zero. Rates for `mid`, `frontier` and `bedrock` are read from `MID_RATE_IN/OUT`, `FRONTIER_RATE_IN/OUT`, `BEDROCK_RATE_IN/OUT` (default 0, i.e. unpriced); I did not put vendor prices in the repo.
- Request replay: `AI_RECORD_REQUESTS=true` (`ai.debug.record_requests`) makes `UsageLoggingModel` put the normalized request on `ModelCalled`, and `RecordModelCall` stores it in the new `recorded_requests` table (migration `2026_01_19_000000`; run `php artisan migrate`). It holds customer text, so it is off by default, `conversations:retain` deletes rows older than `AI_RECORD_REQUESTS_DAYS` (7) and `user:forget` deletes a user's. `ai:compare --replay --judge=<provider>` replays them (requests that offer tools are skipped and counted, because the harness does not run tools; replayed cases keep no answer text in the result file). `ChatRequest` gained `toRecorded()`, `fromRecorded()`, `withFeature()` and `withProfile()`.
- Tiers: `ai.tiers` (`small` = `local`, `mid` = `AI_MID_PROVIDER`, default `mid`, `frontier` = `frontier`), a new `mid` provider (`MID_URL`, `MID_KEY`, `MID_MODEL`, `MID_DRIVER`; unconfigured until you set them), and `Router::tierFor(RouteSignals)` with the book's rule: a human flag or `ai.routing.frontier_after_rounds` (2) unresolved rounds go to frontier; agreement below `ai.routing.mid_below_agreement` (0.67), a multi-part question (two or more question marks) or a billing dispute (a keyword match: dispute, chargeback, charged twice, refund) go to mid; everything else stays small. `Route::$tier` now holds `small`, `mid` or `frontier` (it held the label `local-8b`; `Router::TIER_LOCAL` is gone and one assertion in `RouterTest` was changed to match). `ModelTiers` maps a tier to its provider and falls back one tier down when that provider is not configured, so with nothing configured every question is answered exactly as at ch19. `SupportAssistant` starts a mid-tier reply on the mid provider through the new `ToolRunner::startingOn()`; the small tier keeps using the feature's own provider (`ai.features`), so a feature override still wins. ## ch17

- Agents and multi-step reasoning. `app/Ai/Agents` holds the loop: `AgentRunner::run(Agent, AgentState, ToolContext)` renders a prompt from the state, calls the model with the agent's tool subset, executes each requested call through `ToolRunner::executeCall` (so the Chapter 11 validation, gate, per-conversation limits, audit and idempotency apply unchanged), lets the agent `observe()` the result into the state, and repeats until the model answers without a tool call or a budget ends the run. `InvestigateAgent` is the one agent; `AgentState` is serializable (`toArray`/`fromArray`: goal, facts, steps keyed by call signature, findings, conclusion) and hashes itself for the progress check; `Trace` records goal, decisions, results, budget events and findings with elapsed seconds; `AgentResult` is `done` or `exhausted` with a reason.
- Budgets: `AgentBudget` stops on `rounds`, `tokens`, `time`, `writes` or `no_progress` (two consecutive rounds that leave the state hash unchanged), from `config('ai.agents.{name}')` (`support`, `triage`, `reminder` with the book's numbers; only `triage` is read today). A write counts when a write tool returned ok, so the idempotent no-op second `open_ticket` counts (the model attempted it) and a denied, invalid or failed one does not. ## ch16

- Retrieval depth. Retrieval now runs as stages behind `RetrieverFactory`: stage one is the `PgRetriever` hybrid query, `QueryRewritingRetriever` widens it with rewritten queries merged by `ReciprocalRankFusion`, and `RerankingRetriever` re-scores the top `ai.retrieval.rerank_candidates` (default 20) and keeps the best five. `RetrievalSettings` carries the knobs; the defaults are `AI_RERANKER=sidecar`, `AI_RETRIEVAL_REWRITE=rewrite` and `AI_CHUNK_STRATEGY=parent-child`.
- Parent-child chunks. Migration `2026_01_16_000000_add_parent_child_columns_to_help_chunks_table.php` adds `parent_id` (self-referencing, cascade delete), `kind` (`parent` or `child`) and `context_header`, and rebuilds the generated `search` column so keyword search also sees the context header. `ParentChildChunker` splits each section into child chunks of up to `ai.chunking.child_max_tokens` (200); `ParentChildIndexer` plans, embeds and stores only the children that are new or changed, stores each parent without an embedding, and keeps unchanged children (and any context sentence already paid for) on re-ingest. Retrieval matches children and hands the model the parent section. `help:ingest` gains `--strategy=heading|parent-child`, `--context-headers` and `--source=DIR`; `--strategy=heading` still builds the ch15 index.
- Contextual headers: with `--context-headers`, `ContextualizeChunks` asks the model (`ContextualizePrompt`, model from `AI_RETRIEVAL_CONTEXT_MODEL`, recorded under the `retrieval.context` feature) for one sentence placing the child in its article. The whole article is the cache-breakpoint system message on providers that support breakpoints. The sentence is appended to the child's header (`Heading — sentence`), embedded with the chunk and indexed for keywords. A model that returns nothing fails the ingest with `ContextGenerationFailed`.
- Reranking: `Reranker` has three implementations behind `AI_RERANKER`: `sidecar` (cross-encoder `BAAI/bge-reranker-base` served by `sidecar/app.py` at `AI_SIDECAR_URL`, default `http://localhost:8008`), `lexical` (share of the question's terms found in the passage, computed in PHP, no service needed) and `none`. `docker-compose.yml` gains a `sidecar` service (`ledgerly-sidecar`, bound to `127.0.0.1:8008`, 2 CPUs and 2 GB, on an internal network). `SidecarClient` is the only code that talks to it and turns timeouts and bad responses into `SidecarFailed`; an unknown reranker name throws `UnsupportedReranker`.
- Query rewriting: `QueryRewriter` with `RewriteMode` `off`, `rewrite`, `expand` (several variants) or `hyde` (a hypothetical answer paragraph), each with its own token cap, always keeping the original question first. Questions that contain an identifier (`IdentifierQuestion`: `INV-` and `T-` numbers, "invoice/ticket/payment 123", `#123`, an email address, any run of four or more digits) skip the model and pass through verbatim. Calls are recorded as `retrieval.rewrite` at the deterministic sampling profile; the model comes from `AI_RETRIEVAL_REWRITE_MODEL` or the default.
- Document parsing: `app/Ai/Parsing` routes by extension through `ParserRouter` to `MarkdownParser`, `HtmlParser` (`league/html-to-markdown`), `DocxParser` (`phpoffice/phpword`) and `SidecarPdfParser` (the sidecar's `/parse`, which runs marker and accepts only PDFs up to 25 MB). Anything else throws `UnsupportedDocument`. `ImportedDocuments` feeds the parsed files into the same ingest as an `imports` category. Two composer packages were added for this: `league/html-to-markdown` and `phpoffice/phpword`.
