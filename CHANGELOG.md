## ch25

This is the last chapter of Volume 1. The tag `vol2-start` is not part of this change.

- Triton as a provider. `config/ai.php` gains the `triton` provider (`driver` `triton`; `TRITON_URL`, default `http://127.0.0.1:9000/v1`, the port of Triton's OpenAI-compatible frontend; `TRITON_KSERVE_URL`, empty by default, the KServe v2 HTTP port; `TRITON_API_KEY`, default `triton`, sent in the header named by `TRITON_AUTH_HEADER`, default `x-api-key`; `TRITON_MODEL_ALIAS`, default `chat`, the model directory name; `TRITON_TIMEOUT`; `TRITON_DEFAULT_MAX_TOKENS`, default 512; `TRITON_LICENSE`; `TRITON_GPU_HOUR_COST`; `capabilities` `tools` and `seed`; `unsupported_options` `min_p`, `top_k`, `repeat_penalty`, `num_ctx`) and a `triton` block (`provider`, `image_tag`, `backend`, `tokenizer`, `tool_parser`, `repository`, `models`, `probe_timeout`). `TritonDriver` (`app/Ai/Drivers/TritonDriver.php`) wraps an `OpenAiCompatibleDriver` and changes three things: it authenticates with a header instead of `Authorization: Bearer`, it adds `max_tokens` (the provider's `default_max_tokens`) to a request that carries neither `max_tokens` nor `max_completion_tokens`, and it declares no structured-output capability. It has no `SupportsContextWindowOverride` and no `SupportsGrammar`. `AI_LOCAL_PROVIDER=triton` points the local role (the `small` tier and the four local features) at it; `AI_TRITON=true` on a compatible provider makes `ai:doctor` treat it as Triton.
- `php artisan ai:doctor --provider=triton [--ctx=]` runs `app/Ai/Doctor/Triton`: eleven checks, one class each under `Checks/`. The frontend's `/health/ready` (HTTP 400 means a model is still loading or failed; unreachable also covers a start-up in progress, because the frontend only listens once `tritonserver` has loaded the models), `/v1/models` with the key (401/403 is a key mismatch; stops here on a failure) and, when `TRITON_KSERVE_URL` is set, KServe `/v2/health/live`, `/v2/health/ready` and the server name and version from `/v2`, or a warning that the KServe checks are skipped; the container tag is declared and a release tag (`TRITON_TAG`); the provider's alias is in `/v1/models`; each model of `TRITON_MODELS` is READY in `POST /v2/repository/index`, with the reason when it is not; each model's `/v2/models/{m}/config` (backend, `max_batch_size`, instance count, dynamic-batching window), warning for a model that takes batches but declares no `dynamic_batching` and for a model other than the chat model with no `model_warmup`; `/v1/models` without the key (200 is a warning that the frontend has no authentication, 401 passes); the tool parser (declared `TRITON_TOOL_PARSER`, warning with the exact 400 the frontend raises without `--tool-call-parser`); the provider does not declare `structured` (a failure if it does, because the frontend drops `response_format`); `/metrics` per model (ok and failed counts, average batch size, average queue time) and GPU utilization and memory; a one-token chat round trip that must carry `usage`; and the license. `TritonServerClient` is the non-throwing probe client (one instance for the OpenAI frontend and one for KServe), `TritonMetrics` parses the `nv_` series, and `ProbeClient` gained an optional `headers` argument for the custom auth header.
- How each check knows what it knows. At `triton-inference-server/server` tag `v2.74.0` the OpenAI-compatible frontend is its own Python program (`python/openai/openai_frontend/main.py`) that starts `tritonserver` in-process. It serves `/health/ready`, `/metrics` (`engine.metrics()`, Triton's Prometheus text), `/v1/models`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings` and, in explicit model-control mode, `POST /v1/models/{m}/load` and `/unload`, on `--openai-port` (default 9000). The KServe v2 HTTP and gRPC frontends are opt-in (`--enable-kserve-frontends`, ports 8000 and 8001) and need the `tritonfrontend` wheel, without which the program prints a warning and carries on. Authentication is `--openai-restricted-api '<apis> <header> <value>'` (APIs `inference`, `model-repository`, `metrics`, `health`), a header check by a middleware, not a bearer token.
- The operational layer every server shares.
  - `CircuitBreaker` (`app/Ai/Resilience`): consecutive `ProviderUnavailable` errors per provider, counted once per logical call after `RetryingModel`'s three attempts, kept in the cache store (`AI_BREAKER_STORE`, default the default store, so every Horizon worker shares it). At `AI_BREAKER_THRESHOLD` (3) it opens for `AI_BREAKER_OPEN_SECONDS` (60) and `RetryingModel` refuses calls with `ProviderUnavailable("<provider> circuit open")` without contacting the server; after the window it is half-open, one failure reopens it and a success closes it. A success between failures resets the count; `RateLimited` and `InvalidRequest` do not count; `AI_BREAKER=false` turns it off. `RetryingModel` guards `chat()` and `stream()`; `raw()` is not guarded, so a probe still reaches the server.
  - `FailoverModel` (`app/Ai/Decorators`): `ai.failover` maps a provider name to the provider that answers when it is unavailable, `AI_FALLBACK_LOCAL` for the local role (for example `frontier` or `mid`). The manager wraps only a provider with a configured, known, usable target; the request goes once to the fallback (`Ai::chatWithoutFailover()`, so two providers naming each other cannot loop) without a `model` that only the primary serves (the LoRA adapter name `ProfileMergingModel` adds); a stream that already yielded an event is not re-routed. `UsageLoggingModel` sits inside it, so `model_calls.provider` is the provider that answered.
  - `SupportAssistant` ends a `ProviderUnavailable` that survived failover in `SupportPrompt::unavailableMessage()` instead of a failed job: the reply completes, a `degraded` `model_calls` row records it (`provider` `degraded`, `finish_reason` `degraded`), and the exchange is kept in the conversation. A cached how-to answer is still served, because the semantic cache is read before any model is called; `SupportCacheGate` now treats an unavailable embedding model or classifier as "skip the cache" rather than an error. `support:ask`, `support:ask-batch` and `conversation:replay` still report an unreachable model as a failure (`ToolRunResult::wasDegraded()`), because they exist to show you that.
  - `php artisan ai:doctor --health [--provider=]`: reachable (`/models` answered), loaded (a one-token chat completion succeeded), warm (that first completion took at most `AI_HEALTH_WARM_MS`, 2000), when `ai:warm` last ran, and the breaker state; exit 1 when it is not reachable, not loaded or the breaker is open. It works for any OpenAI-compatible, Ollama, llama-server, vLLM or Triton provider (a Triton one is probed with its header).
  - `php artisan ai:doctor --profile=<name>` checks a Compose profile (`linux-gpu`, `llama-gpu`, `llama-cpu`, `vllm`, `triton`, `monitoring`; the book's `ollama` and `llama` are aliases) against the machine: declared in `docker-compose.yml`, `docker compose` present, an NVIDIA card (through `HardwareProbe`) and docker's nvidia runtime for a profile that needs one, the local role pointing at the provider the profile serves, and the published port free. It does not size the model against the card; `ai:doctor --size` still does.
  - `php artisan ai:warm [--provider=] [--wait=SECONDS]`: sends the support system prompt and a short question twice to every model the provider serves for this app (the provider's model, plus a feature-routed adapter), with `max_tokens` 8 and the `deterministic` profile, through `Ai::chatWithoutFailover()` so a fallback never "warms" the wrong server; prints the second call's time and the prompt tokens the server reports as cached, or says it does not report them; remembers when it ran (for `--health`); exit 1 if it cannot. `--wait` polls `/models` first. Each call is a `model_calls` row with feature `ai.warm`.
  - `php artisan ai:stats` prints two more lines, `breaker:` (the feature's provider and its fallback, with `OPEN (3 consecutive ProviderUnavailable at 14:06:40; retry at 14:07:40)`) and `routed:` (the window's `model_calls` counted by provider, so `semantic-cache`, `degraded` and a fallback sit beside the local provider, then `failed jobs`).
  - `php artisan ai:load --provider=triton` works (the book's Exercise 5): the provider check accepts a Triton provider, the tokenizer comes from `TRITON_TOKENIZER`, and the auth header goes to `vllm bench serve` as `--header`.

- Differences from the book.
  - The book replaces the single Compose file with `ops/compose/` (a base file with the app, Postgres, Redis, Reverb, Horizon, the sidecar and an `ai-warm` service, one file per server, a macOS override, a monitoring file and an annotated `.env.example`). So the profiles stay in the root `docker-compose.yml` (now with `triton` and `monitoring`), there is no `ops/compose/`, no `ai-warm` service or `depends_on` chain (run `php artisan ai:warm --wait=300` before `horizon` in your process manager or deploy script), no macOS override (a Mac developer runs no inference profile, as since ch22) and `.env.example` stays at the root, with the new variables added. The profile names are the repository's (`linux-gpu`, `llama-gpu`, `llama-cpu`, `vllm`, `triton`, `monitoring`), not the book's `ollama`, `llama`, `vllm`, `triton`; `ai:doctor --profile` accepts the book's two as aliases.
  - The book says no inference port is published to the host. Since ch22 this repository publishes each server on `127.0.0.1` only; Triton and Grafana follow that. The KServe port is published too (`127.0.0.1:8010`), and the KServe frontends have no authentication at all, so do not rebind it.
  - The book starts `tritonserver --model-repository ...` and finds the OpenAI frontend on port 9000. At `v2.74.0` the frontend is a separate Python program, as above, and its metrics are on `/metrics` of port 9000 (the book's 8002 is the standalone `tritonserver` binary's metrics port, which I did not check) and its readiness is `/health/ready` on 9000; `/v2/health/ready` exists only with the KServe frontends. The doctor and the Prometheus config use 9000.
  - The book's provider config reads `capabilities => ['structured', 'tools']` and `api_key` as a bearer token. At `v2.74.0` `engine/utils/triton.py` lists `response_format` among the fields excluded from the sampling parameters it forwards to the vLLM backend, so a `response_format` request is accepted and ignored: output is not constrained. Only `tool_choice` with a named or required tool is turned into guided JSON (`_get_guided_json_from_tool`). So the provider does not declare `structured` (`StructuredClient` validates and repairs, as for any provider without the capability) and the doctor fails if it is declared. `CreateChatCompletionRequest` has `extra="forbid"`, so `top_k`, `min_p`, `repeat_penalty` and `num_ctx` would be an HTTP 422; they are dropped through `unsupported_options`. The frontend's default `max_tokens` is 16 (`--default-max-tokens`), and only `support.reply` sets one in this app, so the driver adds a default and Compose passes `--default-max-tokens` too. The response carries `usage` (the backend's `num_input_tokens` and `num_output_tokens`) but no `prompt_tokens_details`, so `model_calls.cached_tokens` is the local estimate; the conformance suite has no Triton row for the structured, cached-token and content-filter cases, and no rate-limit or context-overflow row (the frontend turns errors into HTTP 400 with `{"detail": ...}`, 422 or 500).
  - Errors are `{"detail": ...}` bodies (FastAPI's `HTTPException`), not OpenAI's `{"error": ...}`, except the restricted-API middleware's 401, which uses `{"error": ...}`. The generic mapper already turns 400/422 into `InvalidRequest` and 500 into the retryable `ProviderUnavailable`, so there is no `TritonErrors`; I found no documented context-overflow message to map to `ContextTooLong`.
  - The book's ensemble (Figure 25-4) would not load as written, from reading the configuration docs and the composing models' configs: the reranker has two required inputs (`input_ids`, `attention_mask`) and only `input_ids` is mapped; `passage_ids` has dimensions `[20, -1]` where the reranker takes `[-1]`; and the two steps are independent, so nothing is chained "embed → rerank". `support_pipeline` here maps both inputs of both models and carries one (question, passage) pair per batch row, with the question repeated by the client. That is my reading of the batching rules, not something a Triton server accepted.
  - The book's `build-trtllm.sh` runs `convert_checkpoint.py` and then `quantize.py` from the converted checkpoint, and builds with `--paged_kv_cache enable`. At `NVIDIA/TensorRT-LLM` `v1.2.1`, `examples/quantization/quantize.py` reads the Hugging Face checkpoint and writes a TensorRT-LLM checkpoint itself (the conversion step is redundant), and `--paged_kv_cache` is marked deprecated in `commands/build.py` in favor of `--kv_cache_type paged`; `use_paged_context_fmha` is a plugin option. The script uses the latter forms. The book's `26.10-trtllm-python-py3` is what `python/openai/README.md` at `v2.74.0` names, but `docker manifest inspect` found no manifest for it (or for `26.09` or `26.08`); `25.10-trtllm-python-py3` exists, so the script defaults to that, which means the frontend inside it is older than the source read here. The in-container example paths (`/app/tensorrt_llm/examples`) are the book's and a variable (`TRTLLM_EXAMPLES`). The book's "trtllm profile" is `TRITON_TAG=25.10-trtllm-python-py3 TRITON_BACKEND=tensorrtllm` on the `triton` profile, not a second profile.
  - The batch-size figure the doctor prints is inferences per execution (`nv_inference_count` over `nv_inference_exec_count`), which is how Triton's `metrics.md` defines the two counters (a batch of n is n inferences, a request is counted once however many rows it carries). The book divides `nv_inference_request_success` by the execution count, which agrees only when each request is one row.
  - The book's breaker and fallback live in `RetryingModel` and the ch17 `Router` (`$this->health->isAvailable('local')`). Here `Router` is the vote classifier, so the breaker is in `RetryingModel` as the book says, and the fallback is the `FailoverModel` decorator, which every feature gets (the classifier and extraction as well as the reply), not a choice the router makes. The book counts a failure per exception in a snippet; here one failed call, after its three attempts, is one failure, so three consecutive failed calls are nine HTTP attempts.
  - The book's drill routes how-to questions to a "cache-only" path and billing, bug and account questions to the frontier, and `ai:stats` reports `routed: cache-only 19 · frontier 9`. Here the semantic cache is read first for every question anyway, so a cached answer is served whatever the server's health; there is no category-based routing during an outage (the classifier is the model that is down), and with a fallback configured every uncached question goes to it. `routed:` counts providers, so a cache answer shows as `semantic-cache`. The book's "frontier or a second local profile" is `AI_FALLBACK_LOCAL` naming either.
  - The book's `ai:doctor --health` prints `reachable yes · loaded yes · warm yes (ai-warm ran at 14:02:11) · breaker closed` and, for vLLM, `loaded: yes (KV cache reported)`. Here the three states come from what the server did for any provider (an answered `/models`, a completed one-token request, a first completion under a threshold the book does not give; 2 s is mine), on two lines. `ai:warm` prints the cached prompt tokens the server reports for the repeated prompt rather than "system prompt (440 tokens)", which the server cannot name, and warms the chat models only; Triton's other models need `model_warmup` in their configs.
  - The Grafana dashboard has no breaker panel (the book lists one): the breaker state is in the app, which exports no Prometheus metrics until the book's Chapter 31; `ai:stats` and `ai:doctor --health` show it. - The abstraction layer. `AiHttpClient` is gone. ## ch18

- Queues, jobs and real-time delivery. With `AI_QUEUED_REPLIES=true` (the default) `POST /support/ask` validates, stores a placeholder row in the new `replies` table, dispatches `AnswerQuestion` on the `ai` queue and returns `202` with `reply_id`, `channel` (`reply.{id}`), `conversation_id`, `status` and `queue_depth` (jobs waiting on `ai`, its own included; a warning is logged at `AI_QUEUE_DEPTH_ALERT`, 20). An optional `request_id` (uuid) makes a double submit return the same reply and run one job. `AI_QUEUED_REPLIES=false` keeps the synchronous answer of earlier chapters, and `phpunit.xml` pins it off so the older tests keep their one-call fakes.
- `AnswerQuestion` (unique per reply, `ai` queue, 180 s timeout, 3 tries, backoff 5/15/60) runs `SupportAssistant::answerStreaming()` under the conversation's tenant, so the whole ch17 pipeline (cache, router, retrieval, tools, citation check, memory, summaries) is unchanged; only the model calls stream. `ToolRunner::run()` and `resume()` take optional `StreamTaps` and then use `AiHttpClient::stream()` for every round (which now records the conversation, `ttft_ms`, the context breakdown and a model call id like `chat()` does). A finished reply stores content, sources, `citations_ok` and completion tokens; a retry after success is a no-op; a second attempt clears the buffer and broadcasts `ReplyRestarted`. `failed()` marks the reply failed with a readable message, broadcasts `ReplyFailed` and records a `model_calls` row with finish reason `job_failed` under `support.reply`.
- Streaming: `DeltaBatcher` flushes every 50 ms or 20 deltas. Each flush appends a numbered chunk to `ReplyBuffer` (the cache store `AI_REPLY_BUFFER_STORE`, default store; use `redis`) and broadcasts `ReplyDelta {t, n}` on `private-reply.{id}`. `ToolCallStarted` carries a label ("Looking up your invoice..."), `ReplyPaused` the summary and the approval links, `ReplyCompleted` the sources and citation flag. Broadcast failures are reported and never fail the job (`ReplyBroadcaster`; after one failure the delta broadcasts pause for 5 s, control events always try). The Reverb client has a 1 s connect and 2 s total timeout.
- The stored state is the truth: `GET /replies/{id}` returns status, final content or (while in flight) the buffered chunks, sources, citation flag, pending approvals and feedback. `GET /replies/{id}/stream` is the server-sent-events fallback: it replays the buffer from `Last-Event-ID` or `?after=`, polls every 100 ms, ends on completion, failure or pause, and gives up after 120 s (EventSource reconnects). `POST /replies/{id}/feedback` stores `up` or `down` on a finished reply. Owner only (403), other tenants get 404. The channel authorization is the same ownership check under the tenant scope.
- Pause and resume: a reply whose run holds a call for approval becomes `paused` (`resume_token` is the `pending_tool_calls.run_id`, `paused_at`), `ReplyPaused` goes out and the job ends. The existing `POST /support/approve|decline/{id}` now, for a paused reply, marks it `resuming` and queues `ResumeReply` instead of resuming inside the request; the resumed run streams under the same `ToolRunner::resume()` state and appends to the same conversation. A pending call for a reply that was not queued still resumes inline. `php artisan replies:expire-paused` (daily 03:00) expires replies paused longer than `AI_PAUSED_EXPIRY_DAYS` (7), marks their pending calls `expired` (a later approve answers 409) and tells the browser.
- `/chat`: a Blade page with two plain ES modules in `public/js` (`reply-channel.js`, `chat.js`), no build step. Sign-in form when logged out, then pending (thinking indicator and tool status), streaming, paused (approval card), completed (stored content, source links, citation warning, helpful / not helpful) and failed (retry) states. The transport opens a Pusher-protocol WebSocket to Reverb, authorizes the private channel at `/broadcasting/auth`, falls back to the SSE route if the socket does not subscribe within 4 s, and after a drop fetches `GET /replies/{id}`, merges chunks by number and refetches when a gap appears.
- Queues and workers: Horizon pools `ai-interactive` (queue `ai`, `simple`, `AI_CONCURRENCY` processes: 1 locally, 4 in production by default, timeout 190), `ai-batch` (queue `ai-batch`, `auto`, 1 to 2 processes, timeout 600) and `default`; long-wait alerts at 30 s on `ai` and 300 s on `ai-batch`. The dashboard is closed outside `local` except for the emails in `AI_HORIZON_VIEWERS`. `TriageTicket` (non-interactive) now runs on `ai-batch` with a 180 s timeout and 3 tries. `help:ingest` and its parent-child variant embed in batches of `AI_EMBED_BATCH` (48) through `Embedder::documents()`; `phpunit.xml` pins it to 1.

## ch17

- Agents and multi-step reasoning. `app/Ai/Agents` holds the loop: `AgentRunner::run(Agent, AgentState, ToolContext)` renders a prompt from the state, calls the model with the agent's tool subset, executes each requested call through `ToolRunner::executeCall` (so the Chapter 11 validation, gate, per-conversation limits, audit and idempotency apply unchanged), lets the agent `observe()` the result into the state, and repeats until the model answers without a tool call or a budget ends the run. `InvestigateAgent` is the one agent; `AgentState` is serializable (`toArray`/`fromArray`: goal, facts, steps keyed by call signature, findings, conclusion) and hashes itself for the progress check; `Trace` records goal, decisions, results, budget events and findings with elapsed seconds; `AgentResult` is `done` or `exhausted` with a reason.
- Budgets: `AgentBudget` stops on `rounds`, `tokens`, `time`, `writes` or `no_progress` (two consecutive rounds that leave the state hash unchanged), from `config('ai.agents.{name}')` (`support`, `triage`, `reminder` with the book's numbers; only `triage` is read today). A write counts when a write tool returned ok, so the idempotent no-op second `open_ticket` counts (the model attempted it) and a denied, invalid or failed one does not. An exhausted run is a normal result: it returns the findings so far and the reason.
- Every run is persisted in `agent_runs` (state, budget usage, trace, status `running|done|exhausted|failed`), checkpointed after every round. `AgentRunner::resume(Agent, AgentRun, ToolContext)` continues a `failed` run (for example after the model server was down) from its saved state, trace and budget; any other status throws `AgentRunNotResumable`. `php artisan agent:trace {run}` prints a run as a log.
- Routing: `Router::route($question)` samples the classifier `ai.routing.samples` (3) times through `VoteClassifier` (`ClassifyTicket` now takes an options array; votes use the `assistant` profile, temperature 0.7, as Chapter 9 describes), takes the majority (`CategoryVotes`), and returns a `Route`: automate with a tool subset and retrieval area, decline (`other`), or human when agreement is below `ai.routing.agreement_threshold` (0.67, so a 2-1 split goes to a person with both labels). A vote the classifier cannot produce counts as `other` and is logged. - Retrieval depth. - Parent-child chunks. Migration `2026_01_16_000000_add_parent_child_columns_to_help_chunks_table.php` adds `parent_id` (self-referencing, cascade delete), `kind` (`parent` or `child`) and `context_header`, and rebuilds the generated `search` column so keyword search also sees the context header. `ParentChildChunker` splits each section into child chunks of up to `ai.chunking.child_max_tokens` (200); `ParentChildIndexer` plans, embeds and stores only the children that are new or changed, stores each parent without an embedding, and keeps unchanged children (and any context sentence already paid for) on re-ingest.
